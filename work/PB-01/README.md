## Паспорт темы

Откуда тема: своя.

1. Код темы:swarm
2. Заказчик: Внутренняя инфраструктурная команда
3. Кто вызывает: Внутренние микросервисы компании
4. Ресурсы: CPU и пропускная способность нод
5. Состояния:  active/degraded/offline
6. Четыре сценария: Сценарий 1 (Успешный): Клиент шлет запрос, балансировщик оценивает веса PSO и маршрутизирует запрос на свободную ноду. Сценарий 2 (Адаптация под нагрузку): На слабый сервер приходит слишком много запросов, PSO пересчитывате веса. Сценарий 3 (Отказ ноды): Одна из нод упала, автоматический retry на другую ноду. ценарий 4 (Ошибка валидации): Клиент отправляет запрос без обязательного заголовка или с неверным ключом. Ответ: HTTP 400/401
7. Правило повтора: Передача Idempotency-Key на целевые ноды, чтобы они сами проверяли свой кэш. Запрещено повторно запускать вычислительный процесс, однако разрешено отправлять повторный ответ клиенту.
8. События: Событие Node.Offline
9. Вне работы: В рамках данного API не реализуется настройка реального аппаратного обеспечения, формирование реальной бизнес-логики, реализация защиты нодов на уровне сети.

Приёмка:
- чужой ключ не видит чужое: Сверка X-Api-Key в заголовке с владельцем task_id в базе/памяти. При несовпадении возвращается 403
- повтор не применяет эффект второй раз: См пункт правило повтора
- запрещённый переход статуса отклоняется: Попытка маршрутизации на ноду со статусом offline отклоняется с ошибкой 503. Попытка изменить статус завершенной задачи отклоняется с ошибкой 409 Conflict

## Схема

sequenceDiagram
    autonumber
    participant Client as Клиент (Генератор нагрузки)
    participant API as API-слой (routes.py)
    participant PSO as Движок PSO (swarm.py / fitness.py)
    participant Proxy as Прокси (proxy.py)
    participant NodeA as Сервер А (8 ядер)
    participant NodeB as Сервер Б (2 ядра)

    Note over PSO,NodeB: Фоновый цикл: PSO непрерывно собирает метрики latency и пересчитывает веса частиц

    Client->>API: POST /api/v1/process <br/> Headers: X-API-Key, Idempotency-Key <br/> Body: {"task": "compute"}
    
    alt Ошибка аутентификации или валидации
        API-->>Client: 401 Unauthorized / 400 Bad Request
    else Успешная валидация (Happy Path)
        API->>PSO: Запрос актуальных весов и выбор ноды
        PSO-->>API: Возврат лучшей ноды (например, NodeA)
        
        API->>Proxy: Передать задачу на выбранную ноду
        Proxy->>NodeA: Асинхронная отправка запроса
        NodeA-->>Proxy: Подтверждение приема (202 Accepted)
        
        Proxy-->>API: Задача успешно передана в очередь ноды
        API-->>Client: 202 Accepted <br/> Body: {"task_id": "uuid", "status": "processing"}
    end

## Повтор, граница, профиль

Будет использоваться заголовок Idempotency-Key, если балансировщик видит этот ключ, он проверяет кэш/память: если задача с таким ключом уже ушла на сервер, он просто возвращает старый статус, не запуская процесс заново. Все кроме сервера.

Фронтенд, система добавления серверов, авторизация пользователей, настройка реального аппаратного обеспечения, формирование реальной бизнес-логики, реализация защиты нодов на уровне сети - этого в API не будет

Клиент отправляет POST /api/v1/process и получает 202 Accepted, через какое-то время клиент направляет GET /api/v1/result/{task_id} на балансировщик. Если задача еще не готова, балансировщик возвращает 200 OK и тело процесса и клиент снова ждет, если готова, баланс. отправляет  200 OK с телом готовности. Результаты запроса хранятся в памяти балансировщика.
